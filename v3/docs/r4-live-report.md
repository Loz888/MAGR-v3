## 对照方法与结果解释

两种方案使用相同模型、知识快照、数据库输入、GitHub 代码、工具权限和固定只读工具计划。SQL 专家执行固定的聚合、按订单分组及取消计数查询，并提供真实 typed cell。

多专家方案由 Knowledge 和 Repo 两个模型专家提取来源引文，再由模型综合。单 Agent 方案串行读取相同来源，由一个模型完成综合。它是固定工具计划下的开发对照，不是对无限制 ReAct 或生产通用 Agent 的评测。

| 首轮指标（每组 5 个案例） | 多专家 | 单 Agent |
|---|---:|---:|
| 正常案例通过 | 2/3 | 2/3 |
| 不足/越权案例正确处理 | 2/2 | 2/2 |
| 实际模型调用 | 15 | 5 |
| 输入 token | 21,178 | 16,634 |
| 输出 token | 6,275 | 2,098 |
| 保守费用 USD | 0.013888 | 0.007510 |
| 平均耗时（秒） | 7.5364 | 4.3670 |

每例按多专家、单 Agent 的固定顺序运行，未随机化，冷热缓存与网络波动未分离；耗时仅作描述。

这组小样本没有证明多专家优于单 Agent：首轮成功率相同，多专家调用和费用更多，平均耗时更长。恢复另用 3 次调用、US$0.003171、9.634 秒，单独计入总支出，不混入首轮 A/B 成绩。

## 冻结与独立判定

执行前冻结了五个案例、十个 profile、数据输入、知识与模型配置、GitHub 提交、费用、工具计划、独立 Python Oracle 和实现哈希。Oracle 根据冻结输入计算七项数值和三项结构化结论，并检查真实跨来源引用。答案文件没有进入索引或模型上下文；模型只收到本 Run 实际读取的材料。

代码来自 [cf512bd 的真实应用代码](https://github.com/Loz888/MAGR-v3/blob/cf512bd1e5bedd7d562a513caba326588024b88d/v3/src/mgar_v3/agents/experts.py)，Git blob 为 `4adc1f8a7c66af2e3b0ac2f6085cae36f67b4814`，内容 SHA256 为 `657b09d1935e9fd52f3ef02cca2556efa74911477a6a359da66c30187957fa41`。官方 MCP 实际返回嵌入式资源，本次修复了适配器，并核验资源路径、commit 与 blob 字节哈希。

调查与恢复共读取 13 份 GitHub 代码证据、9 份知识证据、27 份 SQL 结果。负例记录 12 次真实服务端拒绝；撤销资料的 canary 未进入模型输入或输出。SQL 角色按数据库、项目、仓库、身份及数据版本分别隔离，准备另一个案例不会使先前角色失效。

机械 Verifier 继续独立检查实际读取、哈希、定位、权限、typed cell 与引用。Oracle 检查冻结业务问题，不证明任意自然语言推断或复杂因果关系。

## 失败、修复与恢复

金额案例中，Repo 专家被问到需要 SQL 才能回答的跨源数值，真实模型诚实返回空 claims。该响应不满足现有引文 schema，触发一次补证据；达到每任务三次调用后，没有剩余调用用于综合。

修复将模型专家的子问题限制为本来源的政策或代码引文，完整业务问题留给综合步骤。恢复保持原题、数据、价格、源 commit 与 Oracle；新建一次恢复 Run，共享原先批准的 24 次预算，不重置旧计数。失败记录和首轮成绩均保留。

这仍提示后续需要专门验证“重试与综合之间的调用额度分配”，并在新冻结样本上复验改进，避免只对已知案例得出效果结论。
