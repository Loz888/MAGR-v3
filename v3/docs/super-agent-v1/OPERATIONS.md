# Super-Agent 常驻部署与运营方案

状态：目标方案，待 SA20–SA23 实施与实测。这里的服务划分、配置和操作流程不是
当前版本已经具备的一键部署能力。现有本机分析服务继续按原说明运行。

## 1. 用户电脑关机后的运行条件

| 布局 | 用户电脑关机后会怎样 | 适用范围 |
| --- | --- | --- |
| 全部服务/Worker 都在用户电脑 | 接收与执行一起停止 | 本机开发和功能验证 |
| 在线服务器接入/控制，只有本机 Runner 执行 | 继续接收，任务进入等待 Runner；不能继续改本机目录 | 必须访问本机环境的项目 |
| 在线服务器接入/控制，至少一个云端隔离 Worker | 在服务器获得授权的仓库/环境上持续执行 | 首版 Always-on 目标 |

不运行本地大模型的起步测试环境可考虑 4 vCPU、8–16GB RAM、100GB 以上可用磁盘，
模型通过受控外部 API 使用；具体容量、日志/CAS 留存和最大 Worker 数必须压测。
该配置不是已验证的生产容量。首次试用限制为一个仓库、一个群、最多 2 个 Worker。

## 2. 部署单元

| 单元 | 职责 | 持久化/权限 |
| --- | --- | --- |
| Source Gateway/Feishu Receiver | GitHub 验签回调、飞书长连接、来源健康/游标 | 最小平台凭据；向 Engine 提交，不写 Task/授权 |
| Web/API + Engine Controller | 登录、策略、入站事务、Mandate/预算/事件、审查 | 一个有效 PG advisory-lock 写者 |
| Router/Eval + Scheduler | 有预算的候选评估、确定性提交、分配/配额 | 调用 Engine；不能自行批任务/扩权 |
| Coding Worker | Harness 中的项目操作、Job、验证与产物 | 独立工作区/容器、短期作用域票据，无 PG/模型/平台宿主密钥 |
| Dispatcher | 授权通知、评论和已审批 PR，回执/对账 | 分离读/写凭据，固定目的地/动作范围 |
| Watchdog | 来源、租约、积压、费用与进展观测 | 低权限观察和恢复请求，不能重置预算 |
| PostgreSQL + CAS | 业务状态与不可变内容、引用/留存 | 内网、备份、恢复时哈希核对 |
| Redis | 缓存、唤醒、短期速率 | 可清空重建，不存唯一业务事实 |

首版可使用单台在线服务器上的 Compose/服务管理，并将 Worker 放入受限容器；
SA12/SA20 验证服务间凭据、队列与恢复边界。以后按容量拆机器，不需要先引入
Kubernetes。未实测多控制器故障转移前，不通过增加 uvicorn workers 宣称高可用。

GitHub Webhook 可使用仅暴露必要回调的 HTTPS Gateway；飞书长连接可主动向平台
连接，不意味着管理端口需要公开。控制台远程访问使用明确配置的 HTTPS 域名、
TrustedHost/Origin、账户会话和 CSRF；当前仅回环允许列表不能直接作为公网部署。
首个管理员仍须可信本机/隧道引导，不能开放匿名远程抢占注册。

## 3. 第一次配置的目标流程

1. 安装锁定版本、运行迁移，验证 PG/Redis/CAS/沙箱，创建本实例管理员。
2. 配置模型与预算；选择允许哪些来源内容进入模型，未配置时不发付费请求。
3. 创建 GitHub Source：选择 App 安装和单个仓库，校验事件/读取权限与接收通道。
4. 创建飞书 Source：安全输入机器人凭据，核对真实 bot/tenant、已授消息能力，
   选择一个授权群和用户；默认仅 @ 与已订阅跟进，全群接收需要明确启用。
5. 绑定来源用户角色，设置仓库、路径/工具/网络范围、规则、期限和项目共享预算。
6. 保持 Shadow，查看“会忽略/关联/创建/提问”的结果、误触发与实际评估费用；
   此时不启动 Worker、不发群消息、不创建 PR。
7. 通过门槛后由管理员保存新策略版本，先开自动调查，再开隔离修复；通知权限
   单独设置目标话题、结果类别、安静时间、频率与有效期。
8. 验证一次真实群消息→任务→真实工具→结果回原话题。创建 Draft PR 前加载完整
   Diff、确认代码树和测试，再审批具体 payload。

密钥通过安全设置/Vault 管理，不要求在聊天或仓库里填写真实值。平台能力、模型
付费、工作区执行、通知外发和发布分别校验；“来源连接成功”不能显示成全部就绪。

以下是策略结构示意，不能直接提交现有 API：

```json
{
  "schema_version": "super-agent-policy-draft-v1",
  "mode": "shadow",
  "sources": ["github-install-1", "feishu-bot-1"],
  "receive": {
    "conversation_ids": ["authorized-chat-id"],
    "sender_refs": ["feishu:tenant-1:open_id:authorized-user"],
    "messages": "mentions_and_subscribed_followups"
  },

  "execution": {

  },
```

## 4. 日常运营和低打扰行为

默认控制台呈现三件事：系统实际在做什么、哪些事项需要人、消耗和失败是否正常。
日常无需盯每轮模型调用；事件与结果按 Task 展开，可下钻到来源、Job、Diff 和费用。

- 无关/重复/自身消息静默过滤，管理员能查看理由与数量。
- 执行中的正常工具进度在 Web/SSE 展示，不逐条发群。
- 有可用结论、需要关键补充或具体审查时通知；同话题同版本结果只计划一次。
- 夜间普通通知合并延后，重要故障按已授权规则发给操作者，避免整个群被告警淹没。
- 已验证结果和通知投递状态分开：可以是“补丁已验证，通知回执待核对”，不能因
  通知失败就重跑修复，也不能把消息已发送当代码已验证。
- 暂停来源接收、关闭自动任务、撤销执行权和取消一个任务是不同操作，界面说明
  影响和在途结果；紧急停用使新操作停止并触发资源/回执核对。

## 5. 健康、指标和容量

至少观测：Source 连接/最后有效事件/权限/gap、入站与路由积压和最老年龄、Fast Path
丢弃理由、Router 用量/错误/未知、订阅投递、任务队列与饥饿、Assignment 租约、
语义进展与 Job、通知积压/unknown、日预算及跨窗口预占、CAS/磁盘与依赖准备。

心跳证明进程在线，不能证明任务在推进。长测试按照实际 Job 进度/期限判断，避免
Watchdog 把合法耗时工作误杀；相反，持续心跳不能掩盖补丁往返和空搜索循环。
告警和恢复请求有去重/冷却，恢复动作依赖具体已知状态，不用“自动重试全部”。

起步服务目标在 SA00 冻结并在 SA22 测量：健康实例的入站提交 P95 ≤2 秒、有效
订阅内部投递 P95 ≤2 秒、空闲槽位下候选就绪到领取 P95 ≤30 秒。平台网络、模型
首 Token、镜像/依赖准备及排队满载分别统计。暂停/撤权接收与实际执行收尾分开
测量；已发送付费请求不能以界面响应速度推断已撤销。

## 6. 故障处理手册目标

| 现象 | 系统应保留/执行的行为 | 操作者动作 |
| --- | --- | --- |
| 来源离线/权限撤销 | 停止相关补拉与新任务，记录 gap，拒绝继续披露 | 检查安装、scope、群成员和连接，按能力补拉 |
| Router 限流/调用未知 | 已收事件不丢，已知拒绝有界等待，未知保留预占 | 查看关联调用/回执，核账后恢复 |
| Worker 失联 | 租约过期后旧 Worker 被 fence，工作区/Job 待核对 | 复用已知结果，确认未知操作，重新分配 |
| 队列过载/CI 洪水 | 公平排队、合并、限额；不丢已确认事件 | 调整范围/配额/容量，检查因果链循环 |
| 通知回执丢失 | 停在 unknown，不再发相同内容或重做任务 | 查询平台对象/nonce；不支持查询时人工核对 |
| PG/CAS/磁盘故障 | 不 ACK 未提交事件，不输出伪成功，停止危险新操作 | 恢复存储、核对 hash、补交来源与通知凭证 |
| 临时模型或执行预算耗尽 | 保留事件/检查点/未完成项，不重置额度 | 查看共享余额、等待窗口或明确追加新许可 |
| 用户说“先别改数据库” | 验证 actor 控制权，在安全点更新约束并拦截不兼容操作 | 查看指令 received/applied 与已发生变更 |

## 7. 备份、升级、删除与恢复

备份至少包括 PG、CAS、加密密钥/Vault 引用、Source 安装与策略版本、来源游标、
未知回执、Worker manifest/Job/lease 和许可审计。备份有一致性时间点，恢复核对
引用与哈希。恢复旧 DB 后，可能已经发生的远端消息/PR 先对账，不能重发所有 pending。

升级先停止新领取，排空或检查点化任务，保留来源缓冲/重放边界，运行前向迁移，
再恢复接入、调度和 Dispatcher；大版本保留兼容/回退步骤。不能把回滚数据库当
成撤销外部 PR/消息，也不能清空用量后重新执行。

撤权、消息删除和保留期到达需要覆盖来源正文、附件、模型输入审计、Recall 缓存、
Memory、CAS、导出和待发消息。保留最小无正文审计与费用凭证；加密备份按保留策略
到期处理，恢复旧备份后重新应用删除/撤权记录，防止内容复活。

## 8. 从试用到发布

工程重放和真实平台/模型分别记录；先完成受控 72 小时测试，再在获准范围进行
真实渠道至少 72 小时运行和不少于 5 个工作日的团队试用，可在同一试用周期中重叠。
这些包含日历等待，不等于工程师连续投入同样工时。

发布时列出实际支持的来源权限、历史/重放/幂等能力、仓库可见性、语言、平台、
最大已测容量和所有未测项。新来源/多项目/远程 Runner 独立放行；单仓单群成功不
直接推定多租户、高可用或通用无人值守发布已通过。
