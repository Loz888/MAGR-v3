## 实施思路

没有新增全局调度器。Case关联原Thread、调查Run、独立修复Run与原Action；原Engine仍是唯一业务写者，原LangGraph仅编排当前Run。新增记录不复制原执行状态，不授予模型或发布权限。

R4实际读取知识、固定Git源码及typed SQL。模型只选择从实际来源生成的短引用ID，服务端精确渲染完整引用；数值根据实际行、聚合、窗口和Decimal独立重算。事实、引用与数值回执都绑定Run/input/spec，线上检查器不读取设计夹具中的expected字段。

调查结果和原只读报告完成共用同一短事务。修复通过原R5受限函数体、AST和Go沙箱协议，另加本Case实际订单窗口回归。修复Action绑定业务结果和规格hash；每次审批及每个发布子步骤重新验证来源与当前权限。未知调用或交付保留账本，只读对账。

真实调用另有P0独立共享grant；所有费用仍来自原usage_calls。共享调用数和费用上限在原预占事务中检查，旧profile的剩余额度不能重置整轮上限。源码、模型、SQL、知识及输入绑定继续通过原许可约束。

## 遇到的问题与处理

| 问题/失败 | 根因与修复 | 验证方式 |
|---|---|---|
| 调查PASS但不能申请修复 | 目标为draft_pr而尚无Action时，交付投影应是not_started；原适配使用not_requested | 三个正常Case完整交接、20个冻结投影样例 |
| 撤权后读取旧结果抛异常 | 原动作列表会读取已撤销的resolution；投影需先判断来源访问并隐藏受限正文 | 读取前撤权、准备后撤权及提交前竞态 |
| 文件IO进入业务事务 | 原Context evidence解析、动作列表查询会间接读CAS；拆出事务外校验，再在SQL阶段核对权限 | 逐线程事务深度注入，覆盖调查、修复与审批；实际SIGKILL |
| 函数体协议与原补丁来源账本不匹配 | 原propose只识别diff响应；新增确定性function_body_v1转换证明，原响应保持不变 | 原生StructuredModel受控HTTP、费用结算和完整Action来源断言 |
| 新迁移SQL关键字冲突 | 初稿把authorization用作列名；在主库迁移前改为authorization_payload | 新建真实PG数据库迁移及幂等迁移检查；初次失败日志保留 |
| 仅各阶段限额不足以约束整轮 | 多个独立profile仍需要共同的冻结预算；新增P0共享grant及唯一阶段绑定 | 一个共享调用额度阻断其他尚有余量的profile；unknown保留预占 |
| 全部补丁回复无效却无业务失败记录 | 原R5在无候选时进入waiting_input；适配层现在补写当前input/epoch的独立failed结果；passed仍只允许running提交 | [修复前真实PG/Go复现FAIL](failures/invalid-patch-business-before.log)与[修复后PASS](failures/invalid-patch-business-after.log)；已纳入最后30项 |
| 真实入口未启用收费 | 配置只识别字面量1，未启用或true均会拒绝；冻结授权仍需独立校验 | 两次均在预占/HTTP前拒绝，模型次数0；后续仅在授权命令中启用1 |
| 磁盘耗尽导致PG停机 | 当前容器根盘约8GB；VFS沙箱创建会复制文件系统，叠加工具缓存及测试数据耗尽空间 | 保留失败验收；恢复同一PG容器/原卷；核对原750次、US$0.311513、unknown=0 |

存储恢复没有删除原数据库卷。可重建SDK/构建缓存移到临时盘；一个未引用镜像先导出再清理，当前沙箱固定镜像保留。旧私有测试备份的2699个文件逐一校验后保留原路径访问，并另存持久私有压缩归档和恢复说明。失效/弃用测试数据库只在明确为闲置一次性数据库时清理；可读取的内容先私有备份，活跃数据库和最新两个测试数据库排除在外。所有私有备份、连接配置和授权不提交GitHub。

第一轮注册验收期间还完成了共享grant补充，源码指纹发生变化；随后磁盘故障中断PG及JUnit写入。该轮是FAIL，不能作为通过记录。后续以重新冻结的指纹单列全量验收。

## 真实复验范围

v1、v2仅准备、未调用；发现并修补无效补丁判定后冻结v3，旧manifest分别保留。实际执行[v3 manifest](../../../eval/p0-commerce-live-v3/manifest.json)哈希为`7b4b7f46c15c0e19d19276a84df4688aeac76f94d3601ba61b97c42f77ce52fd`，源码指纹为`9f353a52dbad516cf9e050bcf7cac94d3045c671de4662fe194d6e5655ab4afb`。

v3使用自有公开仓库`Loz888/MAGR-v3`的固定提交`6669b7d189aa439bd23334d9b59739f8b48f4406`，全树Git对象与本地提交核对；复用三个v2命名的固定base分支，避免目标写权冲突。已有自有测试Issue #1作为锚点，五个Case使用独立project作用域，不改写原R1/R5 Thread。固定官方GitHub MCP v2.0.3的真实只读探测通过，读写身份由运行环境已有配置提供，不发送给模型。

三个正常场景为重复支付、状态过滤、退款状态；负例为缺少SQL与知识撤权，预期模型调用为0。真实模型最多新增18次，峰值费用预占上限US$0.055296，仓库累计上限仍为原US$2。金额按冻结峰值价格保守计算，不冒充供应商精确发票。

本轮为开发者可见的固定合成业务整合验证；不作为独立盲测、生产HA或多Agent优越性结论。真实报告/候选通过与真实Draft PR交付分开记录，只有准确完整Action获批并核对远端对象后才记录交付通过。
