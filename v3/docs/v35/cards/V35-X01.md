# V35-X01：按需启用 R4 Experts，而非默认三专家

- 状态：DONE（2026-11-10）
- 依赖：V35-R05、V35-M02
- 优先级：P2
- 涉及文件：`routing/experts.py`（新建）、`graph/experts.py`、`repository_analysis/agent.py`、新 `tests/test_v35_x01.py`

## 目标

把多 Agent 从“默认并行三专家”改为“单主 Agent + 按需专家子图”；简单 Bug 不为形式调用专家。

## 实现

### 1. 确定性触发，而非模型决定

- 新增 `routing/experts.py`，与 LangGraph Runner、Repair 编排解耦；`ExpertRouter.route()` 只读 `ExpertContext`，不调用模型。
- 触发信号：多文件变更、依赖边、重复验证失败（≥2 测试文件或 ≥2 失败尝试）、安全问题、信息冲突、用户显式请求；另按任务文本识别 documented/data/repo 关键词，当“文档口径 + 数据指标”同时出现时追加 `cross_source` 并选择 repo 参与对账。
- 无任何信号时返回 `mode="single_agent"`、`roles=[]`；单个 Go 小修复因此零专家调用。

### 2. 专家只读，主 Agent 保留最终决策

- `ExpertAdvisory` 固定 `read_only=True`、`may_write=False`、`main_agent_decides=True`；`ExpertDecision` 固定 `write_access=False`、`main_agent_decides=True`。任何扩权构造被 pydantic 拒绝。
- `ExpertCoordinator` 只返回建议，不写数据库、不修改传入的 `main_state`；`ExpertOutcome.main_state_mutated` 恒为 `False`。
- `RepoAnalysisAgent` 通过可选 runtime hook `expert_advice(spec, revision)` 接收建议，并压缩为最多 3 条、summary ≤600 字、facts ≤4、evidence_ids ≤16；payload 始终显式携带 `main_agent_decides=True`、`write_access=False`。无 hook 时默认 `single_agent`，不产生额外模型调用。

### 3. 触发标准、预算硬上限、停止条件与去重

- `ExpertBudget` 硬上限：`max_experts≤3`、`max_rounds≤3`、`max_calls_per_revision≤3`、`timeout_seconds≤60`，越界构造失败。
- 角色消耗轮数后达到 `max_rounds` 返回 `single_agent` + `ROUND_BUDGET`；角色数超过 `max_experts` 按 repo/knowledge/data 顺序截断并标记 `EXPERT_BUDGET`。
- 每 revision 的调用上限在 coordinator 内硬性扣减；超出时截断为已服务的角色并标记 `CALL_BUDGET`。
- 去重键为 `(role, input_revision, question)`：同一 revision 的重复咨询直接复用缓存，`expert_calls=0`、`duplicates_skipped` 列出角色；缓存命中不消耗调用预算，即使预算已耗尽仍可返回既有建议。
- 并行专家由同一个 `input_revision` 派生；返回的每条 advisory 都携带该 revision。

### 4. 超时、空结论、冲突、失败不污染主流程

- 超时 → `timeout/EXPERT_TIMEOUT`；异常 → `failed/EXPERT_FAILED`；空 summary 且无 facts → `empty/EXPERT_EMPTY`；引用输入之外的 evidence → `invalid_evidence` 且清空 facts；provider 缺失 → `failed/EXPERT_UNAVAILABLE`；revision 不一致 → `failed/EXPERT_REVISION_MISMATCH`。
- 任一降级只设置 `degraded=True` 并保留结构化原因，不阻断主 Agent，也不改写主状态。
- `RepoAnalysisAgent._expert_advice` 对 hook 异常与非 dict 返回分别降级为 `EXPERT_FAILED` / `EXPERT_SCHEMA`，按 revision 缓存，避免重复失败调用。

### 5. R4 图计划阶段接入（保留既有三专家评测路径）

- `graph/experts.py` 的 `plan()` 先经 `ExpertRouter` 计算角色，再生成 `InvestigationPlan`；新增 `expert_route` 事件记录 `mode/roles/signals/reason`。
- 图本身是专家子图，`InvestigationPlan` 至少需要 1 个 task：路由为 `single_agent` 时退化为单 `repo` 角色，不伪造三专家。
- 既有 R4 fixture 问题 “Summarize documented duplicate-count symptoms” 命中 documented/count/duplicate，仍选择三专家，`test_r4_experts.py` 的并行与 join 断言保持不变。
- `workbench/orchestrator.py` 未修改：R03 验收已明确专家辅助是上层可选编排，修复编排只依赖 provider；X01 通过共享 `ExpertCoordinator` 与 Investigation hook 暴露可选能力，避免在编排层出现第二套截断/专家规则。

### 6. 离线双臂对比

- `BenchmarkRow` / `summarize_benchmark()` 消费已记录的 single-agent 与 expert 结果，输出成功率、成本比、延迟比、简单任务专家额外成本与结论。
- 无收益时结论明确为“keep single-agent”，不冒充已有收益；live ablation 留给 V35-E02。

## 负向测试

单个 Go 小修复不触发专家；专家无限循环/重复派发由 `max_rounds`、`max_calls_per_revision` 与 `(role, revision, question)` 去重阻断；专家失败、超时、空结论、冲突、无效证据与 revision 漂移均只产生降级 advisory，主状态与最终决策不变；专家尝试扩权被模型与测试双重拒绝。
