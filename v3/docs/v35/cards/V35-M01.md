# V35-M01：跨 Investigation / Repair / Verify / Publication 的持久经验闭环

- 状态：DONE（2026-11-10）
- 依赖：V35-R03
- 优先级：P1
- 涉及文件：`memory/{loop,retrieval}.py`、`migrations/0026_memory_write_attempts.sql`、`repository_analysis/memory_loop.py`、`repair/{repair_agent,pr_delivery}.py`、`workbench/service.py`、新 `tests/test_v35_m01.py`

## 目标

保留现有四类 Memory 契约与 `knowledge.memory_*` 表；把 R04/R05 的进程内 `EpisodeSink` 适配为持久 `MemoryWriter`。

## 实现

### 1. 既有记忆契约之上做适配，不新建第五个 Store

- 新增 `mgar_v3/memory/loop.py`：
  - `MemoryContext` 固化 `project_id / repository / commit / actor / ticket_id / run_id / task_id / finding_id / evidence_ids / artifact_hashes`。
  - `PersistentRepairMemory` / `PersistentPublicationMemory` 实现 R04 的 `EpisodeSink` 协议，把 `RepairEpisode` / `PublicationEpisode` 转成 `MemoryCandidate` → `MemoryWriter.validate` → `MemoryWriter.write`。
  - 复用 `knowledge.memory_records` + `memory_episodic`；候选类型仍为 working/episodic/semantic/procedural 四类之一，本卡只写 episodic。
- 触发映射沿用 V3.3 CandidateTrigger：
  - `succeeded → patch_tests_passed/success`；`public_tests_failed / patch_rejected / verification_failed / exhausted → patch_verification_failed/failure`；其余失败 → `investigation_completed/failure`。
  - `RepairOutcome(waiting_approval) → patch_tests_passed/success`；`exhausted → patch_verification_failed/failure`。
  - `PublicationEpisode(published) → release_decided/success`；`write_permission_required / base_changed / failed → release_decided/failure`；`cancelled / base_advanced` 不写记忆。

### 2. Task/Run → Finding → Evidence → RepairAttempt → TestReceipt → Memory 可追溯链

- 每个候选先调用 `engine.artifacts.put()` 写入 `v35-memory-trace-v1` trace（含 run/ticket/finding/evidence/attempt/receipt/payload hash），并把 hash 写入 `artifact_hashes`；同时登记 `app.artifacts` 行。
- `record_repair_outcome` 额外合并 `RepairOutcome` 的 attempt 补丁、测试回执、review bundle 工件，`summary` 写入 `attempts=/receipts=/trace=` 摘要。
- `MemoryHit` / `MemoryAdvisory` 新增 `artifact_hashes`，召回结果可直接回溯到 Evidence 与工件；模型只拿到 `reference_only=True` 的摘要。
- 发布回执：`PublicationEpisode` 的 proposal/branch/base_sha/tree_hash/payload_hash/PR 号写入 trace，published 与 write-denied 都落为 `release_decided` 经验。

### 3. 跨 Commit 经验标记需重新验证

- 沿用 `MemoryRetriever.search_memory(query, commit=...)` 在 `scope=None` 时不按 commit 过滤的行为；新 Run 在其他 Commit 召回到历史记录时返回 `version_status="historical"`、`requires_reverification=True`。
- 计划提示（`plan_hints`）只取 `requires_reverification=False` 且 `confidence >= 0.5` 的 advisory；`confirmed_facts` 只允许 `version_status="current"` 且有 evidence 的记录，历史经验不会被伪装成当前事实。
- `AnalysisMemory.recall_task` 继续跳过 `working`；工作记忆只保留在本 Run 范围内，不作为跨任务事实。

### 4. 写入失败可审计、可重试且不破坏业务状态

- 新增 `knowledge.memory_write_attempts`（migration `0026`）：`candidate_id` 主键、candidate JSONB、`status(written/duplicate/rejected/failed)`、`error_code/error_message`、`attempts`、`memory_id`。
- `MemoryWriteAudit.record()` 以 UPSERT 记录每次尝试；`pending()` 返回 `failed` 候选；`retry(candidate_id)` 重新走 `MemoryWriter.write` 并把 attempts+1。
- 校验不通过（`accepted=false`）记 `rejected`；需人工确认的 Semantic/Procedural 记 `rejected`；同 summary 冲突被视为 `duplicate`；其他 `DomainError` 记 `failed`。
- Workbench 的修复/发布记忆调用均包在 try/except：记忆写入失败只记审计与日志，不影响已验证的 task/finding/publication 状态。

### 5. Workbench 接线

- `authorized_repair` 默认注入 `SnapshotRepairRuntime(memory=PersistentRepairMemory)`，并在 `RepairOutcome` 落账后调用 `record_repair_outcome`。
- `_sync_publication` 在终态（`succeeded/exported/failed`）调用 `PersistentPublicationMemory`。
- `_memory_context` 只接受真实 `repair_run_id`/`audit_run_id` 且必须能从 `RepositoryAnalysisStore.spec()` 读回；没有证据链时返回 `None`，宁可不写也不伪造 provenance。
- `DeliveryStatus` 增加 `failed`，使 Workbench 发布失败也能落为发布经验。
