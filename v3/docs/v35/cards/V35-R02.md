# V35-R02：真实仓库源文件与 Docker Sandbox 统一执行

- 状态：DONE（2026-11-10）
- 依赖：V35-R01
- 优先级：P0
- 涉及文件：`repository_analysis/workspace.py`、`repair/{worktree,sandbox_executor,runtime}.py`、`workbench/service.py`、`deploy/r03/*`、新 `tests/test_v35_r02.py`

## 目标

让 Handoff 从固定 Commit 的仓库快照建立独立修复 Worktree；Live Repair 只在受限 R03 Docker 中执行测试。

## 实现

### 1. 固定 Commit 的字节级快照

`RepositoryWorkspace.snapshot()` 产出 `RepositorySnapshot`（`snapshot_version=v35-repository-snapshot-v1`）：

- 只接受 Git 索引中 `kind=blob` 且 mode 为 `100644` / `100755` 的路径；逐文件重算 Git blob SHA-1，并与索引登记值比对，不一致返回 `WORKSPACE_FILE_MISMATCH`。
- 每个文件同时记录 SHA-256；含 NUL 或非 UTF-8 的内容进入 `binary_paths`，修复工作区拒绝二进制快照（`PATCH_SNAPSHOT_BINARY`）。
- 读取前逐段拒绝符号链接（`WORKSPACE_SYMLINK_DENIED`）、拒绝 `resolve()` 逃逸工作区根、拒绝缺失文件。
- `git rev-parse <commit>^{tree}` 必须等于 `HEAD^{tree}`（`WORKSPACE_GIT_MISMATCH`）；总字节超限返回 `WORKSPACE_SNAPSHOT_TOO_LARGE`。
- `snapshot_hash = digest(snapshot 内容)`，可脱离数据库重算。

### 2. Handoff ↔ 快照 ↔ Worktree 绑定

- `RepairRequest.from_handoff()` 校验 `handoff.computed_id()`、repository、`base_commit == snapshot.commit`、`reproduction.commit == snapshot.commit`，并逐文件核对 `sha256_text`；任一不符分别返回 `REPAIR_HANDOFF_CORRUPTED` / `REPAIR_REPOSITORY_MISMATCH` / `REPAIR_COMMIT_MISMATCH` / `REPAIR_SNAPSHOT_MISMATCH`。
- `PatchWorktree.from_snapshot()` 校验仓库、Commit、文本覆盖完整性与每文件 SHA-256；初始化时重建初始树并要求等于 `snapshot.tree`，否则 `PATCH_TREE_MISMATCH`。因此每个补丁回执的 `tree_before` 均可由快照单独重算。
- `RepairRequest` 的 `handoff_id` / `base_commit` / `source_tree` 全有或全无；`RepairAgent` 应用补丁时把 `source_tree` 作为 Worktree 的期望初始树。

### 3. 统一运行时：Handoff → 快照 → Worktree → Docker

新增 `repair/runtime.py` 的 `SnapshotRepairRuntime`：

1. 重算 `snapshot.computed_hash()`，与 `snapshot_hash` 不符返回 `REPAIR_SNAPSHOT_CORRUPTED`；
2. `RepairRequest.from_handoff()` 建立绑定；
3. 复用 `RepairAgent`，其 `SandboxExecutor` 在受限 R03 容器内执行 baseline、公开测试与隐藏验证。

基线失败才调用提供方；基线通过返回 `baseline_not_reproduced`（提供方调用数为 0），依赖缺失返回 `waiting_for_dependencies`，测试回执保留 `build_failed` / `test_failed` / `timeout` / `sandbox_error`。

### 4. 切断 Live Repair 对 fixture / 宿主 pytest 的依赖

`WorkbenchService._fixture_tests()` 首行检查 `execution_mode != "fixture"` 即抛 `WORKBENCH_LIVE_REPAIR_SANDBOX_REQUIRED`（409）。Live 路径不再读取 `_fixture_files()`、不经过 `FIXED_DISPATCHER`、不在宿主启动 `pytest`；测试通过 monkeypatch 记录全部 `subprocess.run/Popen` 调用，断言无 `sys.executable`、无 `-m pytest`、无 `mgar-u01`。

### 5. 容器策略、状态与清理

- 测试命令只由 `GoAdapter` / `PythonAdapter` 生成：`GO_COMMAND` 与 `/usr/bin/python3 /opt/mgar/runner.py --root /workspace`；模型文本永不进入 shell。
- 镜像由 `.local/r03/sandbox-lock.json` 的 `image_id` 锁定；启动后 `docker inspect` 逐项核验 `network=none`、只读根、`Binds`/`Mounts` 为空、非 root（65532:65532）、`cap-drop=ALL`、`no-new-privileges`、`pids/memory/memory-swap/cpus/ipc` 与 tmpfs 白名单，并对环境键做密钥正则扫描（`secrets_injected=false`）。
- 每次执行在 `finally` 中 `docker rm -f`；`SandboxExecutor` 支持上下文管理，异常路径也回收；`reclaim_stale()` 按 `mgar.v3.r03.sandbox` owner label 清理崩溃遗留容器。
- 依赖缺失不联网：Go 无 `vendor/modules.txt` 或 Python 检测到第三方导入/清单时返回 `waiting_for_dependencies`，命令为空、不创建容器。
