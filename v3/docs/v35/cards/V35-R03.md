# V35-R03：统一 Audit & Repair 多轮编排

- 状态：DONE（2026-11-10）
- 依赖：V35-R02
- 优先级：P0
- 涉及文件：`workbench/orchestrator.py`、`workbench/service.py`、`repair/repair_agent.py`、`repair/runtime.py`、新 `tests/test_v35_r03.py`

## 目标

把 Workbench 从“只读 Audit”扩展为**具备独立修复授权才允许**的 `audit_and_repair` / `issue_repair`；默认仍拒绝写操作。

## 实现

### 1. 独立修复授权与默认拒绝

- `WorkbenchService.authorized_repair()` 是唯一入口，先过 `_authorized_repair_gate()`：任务必须处于 Live 路径（`execution_mode != "fixture"`）且为可修复状态；Handoff 内容寻址 ID 必须与内容一致；Handoff 的仓库、Commit、finding、`source_commit` 必须与当前 finding/快照一致；快照 `commit` 与逐文件 SHA-256 必须可重算一致；最后调用 `RepairAuthorization.validate_scope()`，校验 `allow_repair`、有效期、仓库、actor 与预算。
- 授权是**独立开关**：`allow_repair=False` 的 Handoff 直接返回 403 `REPAIR_AUTHORIZATION_DENIED`，不会创建 checkpoint、不会调用 provider、不会创建容器。
- 编排器 `AuthorizedRepairOrchestrator._authorize()` 在运行时再次执行同一组校验（Handoff 内容 hash、finding/handoff 绑定、快照一致性、`validate_scope`），不依赖上层 Service 的单次判断。
- 授权通过后以幂等键把任务依次推进 `queued → investigating → suspected → reproduced → repairing`，每一步写 Workbench 事件与 Run 状态。

### 2. 检查点账本与中断恢复

- 新增 `RepairLedger` 协议与两个适配器：
  - `JsonRepairLedger`：`<task>-<finding>.json` 原子替换写入（`os.replace`），内容寻址 artifact 目录；
  - `WorkbenchRepairLedger`：checkpoint 以 `kind="repair.checkpoint"` 追加到既有 `workbench_events`，artifact 存入 PostgreSQL 的 artifacts 表，`idempotency_key=repair-checkpoint:<finding>:<seq>`。
- `_CheckpointObserver` 在 RepairAgent 报告的每个节点边界持久化：`baseline_started`、`baseline`、`provider_started`、`planned`、`patched`、`receipt`、`attempt`。每个 checkpoint 记录 attempt、test_runs、baseline/plan/patch/receipt/attempt artifact hash、phase 与 node。
- 恢复时 `_ReplayProvider` 优先重放已记录的 `PatchPlan`（从 artifact 反序列化）或已记录的结构化拒绝；同一 attempt 若进程停在 provider 调用中，返回不可重试的 `REPAIR_UNKNOWN_PROVIDER_OUTCOME`，**不盲目重复可能已发生的付费调用**（`allow_unknown_repeat=True` 才允许显式重复）。
- 重放补丁若树或 `patch_id` 与记录不符，抛出 `REPAIR_PATCH_DRIFT`；恢复测试断言 provider 调用次数为 0、patch_id 与中断前一致。

### 3. 预算、失败分类与回滚

- `RepairBudget` 的 `max_attempts`、`max_test_runs`、`deadline_seconds` 写入 checkpoint 与 Task/Run Ledger；每次 baseline/public/verification 回执都累加 `test_runs`，累计超预算立即停止并返回 `budget_exhausted`。
- 覆盖的终态：`waiting_approval`、`baseline_not_reproduced`、`waiting_for_dependencies`、`sandbox_error`、`exhausted`、`budget_exhausted`、`deadline_exceeded`、`provider_error`、`cancelled`、`base_advanced`；结构化输出含 `failure_stage` / `failure_code`、每轮回执与拒绝原因。
- 失败轮次不会保留 PatchWorktree 修改：Service 在失败/取消路径把 finding 回滚到 `reproduced` 阶段，仅保留公共可见的结构化反馈。
- 隐藏验证文件与测试名只存在于 `AuthorizedRepairJob` 与运行时验证阶段；`RepairPrompt` 仅含公开文件、目标、允许路径与限额，测试断言 provider 收到的 prompt 不包含任何验证文件内容或测试名。

### 4. 取消与迟到回执

- `RepairCancelToken` 在每个节点边界检查；取消时抛出 `RepairCancelled`，携带阶段、attempt 与已经产生的回执。
- 若取消发生在测试执行期间，测试进程仍会返回回执：该回执写入 `discarded_receipts`，但不生成 Review Bundle、不推进 finding；重放运行对同一取消状态保持惰性（provider 0 次）。

### 5. 完成即 `waiting_approval`，不直接发 PR

- 成功路径用最终接受的补丁在内存中重放文件内容，`seal_bundle()` 生成 Review Bundle（含 base SHA、最终 tree hash、diff、changed files、Patch ID、测试回执 ID），bundle 写入 artifact 账本。
- Service 将 baseline 回执映射为 `reproduction`、public 回执映射为 `FixRecord`（同命令、同测试集、diff/diff_sha256、前后 tree SHA-256），finding 推进 `repairing → patch_verified → waiting_approval`，并登记 `pending` ApprovalRecord。
- 全链路不创建分支、不 push、不调用 GitHub：`live_github_write_gate = NOT_RUN`。

### 6. 专家辅助可选

- 本卡不把三专家作为前置条件：`AuthorizedRepairOrchestrator` 只依赖 provider 协议，简单缺陷用单提供方即可完成。专家辅助仍作为上层可选编排，未在测试中强制参与。
